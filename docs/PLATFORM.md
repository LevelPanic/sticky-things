# How macOS and iOS handle clipboards, drags, files and extensions (and what we do about it)

These are research notes, checked against macOS 26.1 and iOS 26 where marked, behind the decisions in this codebase. Each section ends with what Sticky Things does about it.

## The pasteboard is a list of items, each with many types

* **Items and types.**
  * `pasteboardItems` has one `NSPasteboardItem` per copied thing. Finder writes one per file.
  * Each item lists its types (UTIs) in the order the source app wrote them.
  * `NSPasteboard.types` is the union of all items, plus legacy aliases the system adds.
  * The board-level `data(forType:)` reads only the first item, except for text, which is joined across items.
* **Lazy ("promised") data.** An app can write a type lazily. Reading it makes that app produce the data while we wait, and there's no reliable way to tell it apart from eager data.
* **Reading changes things.** Some types have side effects: Word inserts bookmarks when asked for `com.microsoft.Link-Source`/`ObjectLink`. Universal Clipboard items are fetched from the other device when read.
* **Sizes.** Apple sets no limit. Web archives can be tens of MB.

**We** read every item × every type, per item, and check `changeCount` before and after (retrying if it changed). We skip three kinds of type:

* **Bookkeeping:** file-promise and marker types.
* **Stale references into another app:** `com.apple.finder.noderef`, Photos object references, Chromium tokens.
* **Unsafe or oversized:** Word's link types, web archives when HTML is present, and anything over 64 MB.

## Pasteboard privacy (macOS 15.4+)

* **The alert.** Apple has announced an "allow paste" alert for apps that read the general pasteboard in code.
* **What's exempt.** A paste that is *user-initiated and paste-related* is exempt: the Edit ▸ Paste menu item and its ⌘V shortcut.
* **`NSPasteboard.accessBehavior`** reports the current setting: `default`, `ask`, `alwaysAllow` or `alwaysDeny`.
* **Status.** On this Mac (26.1) it reports `alwaysAllow`, and the alert isn't on by default yet.
* **Testing it.** Developers can opt in with `defaults write <bundle-id> EnablePasteboardPrivacyDeveloperPreview -bool yes`.

**We** never read the clipboard in the background. Capture happens only on ⌘V (routed through the main menu's Edit ▸ Paste) and on drag and drop (drag pasteboards are always allowed).

## Polite clipboard citizens (nspasteboard.org)

| Marker | Meaning | What we do |
|---|---|---|
| `org.nspasteboard.ConcealedType` | A secret (Chrome, Firefox, 1Password 8, Enpass…) | Saved only because you pasted it on purpose. The preview stays blurred until you point at it. Given back with the marker and `.currentHostOnly`, so it never syncs over Universal Clipboard. |
| `org.nspasteboard.TransientType` / `AutoGeneratedType` | Not a real copy | Dropped from the stored data. |
| `org.nspasteboard.source` | Bundle ID of the app it came from | Used to credit the source. Set to the original app when we give the item back. |

## Drag and drop

* **Type matching.** AppKit matches the registered drag types exactly, so we register a broad list (`DropTypes.all`) plus `NSFilePromiseReceiver.readableDraggedTypes`.
* **File promises.**
  * Photos, Safari images, Preview's sidebar page thumbnails and Mail attachments arrive as **file promises**, and Apple's samples prefer them: they're the original asset.
  * All receivers in one drag share one destination folder.
  * The reader block runs on our queue.
  * Some apps deliver fewer files than promised, or none, so we time out after 30 s.
* **Preview.**
  * The title-bar proxy icon gives a file URL.
  * Sidebar thumbnails give a promise of "Doc (dragged).pdf".
  * ⌘C on a rectangular selection gives PDF + TIFF.
  * Never pass PDF data through `NSImage`, which rasterizes it.
* **Finder.**
  * Each file is its own item with a `public.file-url`.
  * The pasteboard also carries the *icon* as TIFF data, so file URLs must always be checked before image data.
* **Our own drags.** The drag's source is non-nil when it started in our app, so we reject it.

**We** use an AppKit drop view as the panel's content (the SwiftUI hosting view is its subview) and no SwiftUI drop modifiers. Promises are received first; everything else is captured synchronously.

## Dragging into the corner

* **No global drag notification.** AppKit tells a view when a drag enters *it*, but not that a drag started in another app. There is no public `NSDraggingSession` to observe from outside the source app.
* **What is readable.** `NSEvent.pressedMouseButtons` and `NSEvent.mouseLocation` are process-wide, and a global monitor for `.leftMouseDown` does not need Accessibility permission (only key events do).
* **We** notice the button going down, then sample it and the pointer while it is held. Moving a few points counts as a drag; a click does not. The corner only grows to its catch area while that says a drag is in progress, so at rest it stays the same tiny target. `DragSessionWatcher` owns this; `CornerWindow` decides what to do with it.
* **A new window under a drag.** A drag's destination is the window under the pointer. When the panel appears while the button is still held, the pointer may need to move before AppKit sends the new window `draggingEntered`. The panel opens adjacent to the corner and the corner still accepts the drop, so either path saves the item.
* **Opening for a drag stays passive.** `showForDrop` orders the panel front and animates it in without `makeKey` and without activating the app, so the drag's source keeps its keyboard and the drag session is not disturbed.

## Giving things back

* **Item structure.** Replay the item structure and type order exactly. The system regenerates legacy aliases itself.
* **Files: never hand out the stored copy.** Finder's ⌥⌘V (Move Item Here) *moves* the pasted file. We hand out an instant APFS clone from an outbox folder instead.
* **Dragging out.** Writes a real file (with the right name) plus every stored data type, so Finder, Mail, Messages and editors each get what they prefer.

## Files

* **Cloning.** `FileManager.copyItem` clones on APFS when the source and destination are on the same volume: instant, and no extra space.
* **Cloud placeholders** (iCloud, Dropbox, OneDrive) are "dataless", and reading them blocks while they download. We detect them with `lstat` (`SF_DATALESS`, per TN3150), link instead of copying, and ask iCloud to fetch them.
* **Bookmarks** follow moved and renamed files on the same volume (no security scope needed outside the sandbox).

## Windows, focus and hover

* **Background apps and the keyboard.** A key `.nonactivatingPanel` takes the keyboard without changing the frontmost app (Maccy and Spotlight work this way). `makeKey` succeeds after a user event aimed at us (the hotkey, a click on our corner). Opening via URL can race activation, so we fall back to activating and hand focus back on close.
* **Initial focus.** When a window becomes key, AppKit focuses the *first* text field. We focus the composer explicitly.
* **Hover.** SwiftUI's hover tracking already uses `.activeAlways`. There are two enemies:
  * **Transparent pixels** pass the mouse through to the window behind. So the panel catches every mouse event (`ignoresMouseEvents = false`) and sits on real glass. Tooltips also need `allowsToolTipsWhenApplicationIsInactive`.
  * **Hit testing.** `.onHover` follows whatever view is on top. If the hover-revealed buttons are an overlay *above* the view with `.onHover`, reaching them counts as leaving, so they hide, the card is hovered again on the next move, and so on: buttons that flicker and vanish when the pointer rests. Put `.onHover` *after* any overlay that holds buttons.
  * SwiftUI reads the real cursor position, so synthetic mouse-moved events don't produce hover. Real hover can only be checked by hand (or with event-posting permission).
* **Text views inside SwiftUI** (the inline editor):
  * `textDidEndEditing` only arrives after the text changed. Clicking away from an untouched editor sends nothing, so the editor ends on `resignFirstResponder` instead.
  * AppKit doesn't resign a first responder that is removed from its window, and SwiftUI doesn't reliably call `dismantleNSView` (it keeps and reuses platform views). The editor also ends on `viewWillMove(toWindow: nil)`.
  * SwiftUI may hand back the *same* `NSView` for the next edit. Each edit gets a fresh identity (`.id(editSession)`) so it starts with a new editor.
  * **A growing card in a lazy list can make SwiftUI build two platform views for one edit.** They both attach, then one resigns first and can rip the edit away from the other. `InlineEditHandle` tracks every live view for one edit token: a duplicate leaving does not finish the live edit, Save still reaches the survivor, and an editor from a different edit still saves when it finishes late. A measurement copy with zero width never attaches or takes focus, and its height calculation is ignored.
  * `makeFirstResponder` right after `makeNSView` often runs before the view is in a window. The editor takes focus in `viewDidMoveToWindow`.
* **Clicks that don't move focus.** Clicking a field that already has the keyboard changes nothing AppKit reports (no `becomeFirstResponder`), and clicking a SwiftUI view that isn't focusable leaves the first responder alone. So "where you're working" can't be read from focus: text fields report clicks from `mouseDown`, and the panel's background takes a tap gesture that SwiftUI only fires when no card, button, chip or field took the click.
* **Testing clicks.** AppKit views (our text fields) accept synthesized `NSEvent` clicks. Post the matching mouse-up first, so the text view's click-tracking loop ends. SwiftUI controls ignore synthesized clicks, so the self-test reaches them through accessibility, and the background tap only through the action it runs.
* **Decoration and permissions.** Reading the desktop picture (`NSWorkspace.desktopImageURL`) means reading a file wherever the user keeps it. In Desktop, Documents or Downloads, macOS shows a Files & Folders prompt ("would like to access files in your Desktop folder"). The corner preview is drawn instead (`ScreenPreview`), and a lint rule bans `desktopImageURL`.
* **Native Settings in a plain `NSWindow`.** Host the SwiftUI `NavigationSplitView` in an `NSHostingController` with `sceneBridgingOptions = [.toolbars, .title]` and a `.fullSizeContentView` window: the sidebar runs under the window buttons and `navigationTitle` becomes the toolbar title.
* **Window shape.** `NSGlassEffectView` as a borderless window's content draws its shadow into the window's square corners. macOS then sees a rectangular window and outlines it. The panel's content view clips to the rounded shape (`cornerRadius` + `masksToBounds`, continuous curve), so the corners stay fully transparent and the system shadow follows the curve.
* **Capturing our own windows.** An app may capture its *own* windows without Screen Recording permission (`CGWindowListCreateImage` with the window's number, looked up at runtime because the SDK marks it unavailable). The self-test uses this to check the panel's corners.
* **Quick Look.** `QLPreviewPanel` only takes the keyboard when the app is active, so we activate for previews. It raises itself above our panel automatically.

## iOS: paste, extensions and system entry points

* **Paste privacy.** `UIPasteboard.general` reads outside a user action can trigger the system paste banner or prompt. The iOS composer pastes only through the system edit menu in its text field, so access follows an explicit paste. The app never reads the pasteboard in the background.
* **Share extensions are separate processes.** A Share extension cannot see the app's sandbox. Both targets declare the App Group `group.app.stickythings`, and `StickyAppGroup.paths` gives them the same SQLite, blob and file directories. The extension normalizes `NSItemProvider`s into the same `CapturedClip` the Mac pasteboard produces, then saves through the shared `CaptureService`.
* **Files from other apps.** Share and drop providers usually hand over a temporary file or a security-scoped URL. The extension copies or scopes the file while it is valid, and `FileLibrary` keeps the library's own copy.
* **Action Button, Control Center and Lock Screen.** iOS 18 controls are WidgetKit extensions. The control uses an `OpenIntent` that must be a member of both the app and the widget extension. It writes a small App Group flag and the system opens the app directly, which avoids the custom URL scheme's "Open in Sticky Things?" confirmation.
* **Home Screen widgets.** A normal `Widget` cannot share its extension with a `ControlWidget`; Sticky Things ships `StickyThingsWidget` for the Home Screen and Lock Screen accessories and `StickyThingsWidgets` for the control. Both use the App Group. The app calls `WidgetCenter.shared.reloadAllTimelines()` after writes, and the timeline re-renders on relative time even without a reload. Timelines are capped at six items, concealed items are excluded, and image blobs are downsampled to 420 px before they enter an entry.
* **Locked capture.** The app does not expose a locked camera capture extension. A control that opens the composer requires the device to unlock, which is the right privacy boundary for a personal library.
* **Siri, Shortcuts and Spotlight.** App Intents and App Shortcuts expose New Sticky Thing and Save to Sticky Things. `CSSearchableIndex` keeps a private on-device index of item titles, captions and text. Spotlight results carry the item id and open the detail screen. Concealed items are excluded.
* **System pickers.** `PhotosPicker` and `.fileImporter` run out of process, so the app does not ask for photo library or file access just to receive what someone picked.
* **Fast launch.** The first SwiftUI frame is the shell plus the persistent composer. SQLite opens in the first view task, not in `Library.init`; garbage collection, the legacy import and Spotlight indexing wait until after the list can render. The launch screen uses the app background color (`LaunchBackground`), so there is no white or black flash before the first frame. The Action Button path focuses the composer without presenting a sheet.
* **One design system across iOS processes.** The app, Share extension and Home Screen widget compile `StickyIOSDesign`. It uses semantic UIKit colors and Dynamic Type styles, so system dark mode, Increase Contrast and text size apply in those processes without each target reading settings. Paper and ink are the only brand colors; controls otherwise use system surfaces and button styles. The Control widget uses the system control style.
* **Quick Look and sharing.** Files are previewed with Quick Look and handed to the system share sheet. Images and PDFs that exist only as blobs are written to a temporary preview file with the right extension.
* **iPad.** Drag and drop is a first-class input: text, URLs and files can be dropped into the list, and rows provide an `NSItemProvider` for dragging out. Pointer and hardware keyboard support come from the native SwiftUI controls.
* **Simulator limits.** The simulator builds the control and extensions but cannot assign the Action Button or exercise the Control Center picker. Those need a signed device build. The share sheet can be exercised in the simulator after installing the extension.

## Hot Corners

* **No API for apps.** The Hot Corners menu is a fixed list stored in `com.apple.dock` (`wvous-<tl|tr|bl|br>-corner`; 14 = Quick Note), and there's no way for an app to add itself.
* **Our approach.** Watch the corner ourselves, then read those keys to warn about conflicts. Offer to set the conflicting one to "–" (1) and restart the Dock, or deep-link to the settings: `x-apple.systempreferences:com.apple.Desktop-Settings.extension?HotCorners`. The `HotCorners` anchor comes from the pane's own `DesktopSettings.searchTerms`.
